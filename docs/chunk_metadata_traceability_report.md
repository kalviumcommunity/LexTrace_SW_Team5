# LexTrace Chunk Metadata & Source Traceability System

## Executive Summary
In Retrieval-Augmented Generation (RAG) applications, retrieved context chunks must be verifiable and traceable back to their origin. Un-tagged text chunks prevent models from generating accurate citations, lead to hallucination risks, and eliminate the ability to filter document subsets by section, format, or page.

This component implements a standardized, corpus-wide metadata tagging engine, automated section and page extraction, a uniform metadata dictionary schema, and an exact-offset `ChunkTracebackEngine`.

---

## 1. Structured Metadata Schema (`ChunkMetadata`)

Every chunk generated by `DocumentChunker` encapsulates an instance of `ChunkMetadata`, guaranteeing that **100% of chunks in the corpus share an identical dictionary structure**:

| Field | Type | Required | Description | Example |
|---|---|---|---|---|
| `source_id` | `string` | Yes | Relative file path / document identifier | `"data/sample_corpus/employee_handbook.txt"` |
| `section` | `string` / `null` | Optional | Active section heading or header title | `"1. Code of Conduct"` |
| `page_number` | `integer` | Yes | 1-indexed document page number | `1` |
| `chunk_index` | `integer` | Yes | 0-indexed position within parent document | `0` |
| `start_char` | `integer` | Yes | Character start offset in document text | `142` |
| `end_char` | `integer` | Yes | Character end offset in document text | `430` |
| `file_type` | `string` | Yes | Source file format (`pdf`, `html`, `md`, `txt`) | `"txt"` |
| `char_count` | `integer` | Yes | Total character length of chunk text | `288` |
| `token_count` | `integer` | Yes | Exact tiktoken count (`gpt-4o-mini`) | `58` |
| `strategy` | `string` | Yes | Algorithm (`fixed_window`, `recursive_semantic`) | `"recursive_semantic"` |
| `created_at` | `string` | Yes | ISO 8601 UTC timestamp | `"2026-09-01T13:13:35.737Z"` |

---

## 2. Section Header & Page Extraction

`DocumentChunker` includes context-aware extractors that parse preceding document text up to each chunk's `start_char`:

1. **Markdown Headings**: Regex parsing of `#`, `##`, `###` headers in Markdown documents (`system_architecture.md`).
2. **HTML Header Tags**: Regex parsing of `<h1>`..`<h6>` and Q&A classes (`faq_guide.html`).
3. **Numbered Sections**: Rule matching for `1. Title`, `Section 2: Title` patterns (`employee_handbook.txt`, `company_policy.pdf`).
4. **Page Number Identification**: Scans for `Page X of Y` or `- Page X -` markers across paginated documents.

---

## 3. Source Traceability Engine (`ChunkTracebackEngine`)

The `ChunkTracebackEngine` enables direct verification of retrieved chunks against raw source documents:

1. **Identity Matching**: Confirms chunk `source_id` aligns with target `LoadedDocument`.
2. **Character Offset Verification**: Extracts `doc_text[start_char:end_char]` and checks text alignment.
3. **Context Window Extraction**: Retrieves surrounding character context (e.g. ±100 chars) for UI highlighting.
4. **RAG Citation Formatting**: Generates IEEE/APA-style citation strings suitable for model responses:
   ```text
   [Source: data/sample_corpus/company_policy.pdf | Section: '1. Scope and Applicability' | Page: 1 | Pos: #1 | Chars: 0-365]
   ```

---

## 4. Metadata Filtering Support

By maintaining uniform keys across all chunks, downstream vector stores (e.g., ChromaDB) can execute structured metadata filters before similarity search:

```python
# Example ChromaDB metadata filtering query
results = collection.query(
    query_texts=["security incident reporting"],
    n_results=3,
    where={
        "$and": [
            {"file_type": "html"},
            {"section": {"$ne": None}}
        ]
    }
)
```
