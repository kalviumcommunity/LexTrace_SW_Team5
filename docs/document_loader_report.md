# Multi-Format Document Loader Technical Report

## Executive Summary

The **LexTrace RAG Assistant** relies on ingesting knowledge from heterogeneous document formats — including PDFs, HTML exports, Markdown files, and plain text documents. To build an accurate vector search index and provide verifiable citations in RAG answers, raw documents must be transformed into a standardized, plain-text representation tagged with immutable source metadata.

This technical report documents the architecture, implementation, error recovery mechanics, and empirical verification of the `DocumentLoader` module.

---

## 1. Why Documents Must Be Converted to a Common Text Form

In a Retrieval-Augmented Generation (RAG) architecture, downstream components (embedding models like `text-embedding-3-small` and LLMs like `gpt-4o-mini`) operate strictly on sequence of text tokens.

Raw document formats introduce major complexities:
- **Binary/Layout Overhead**: PDFs store visual positioning coordinates, font streams, and vector graphics rather than contiguous text sentences.
- **Markup Noise**: HTML documents contain structural tags (`<div>`, `<script>`, `<style>`, `<nav>`) that introduce non-semantic noise and artificially inflate token count.
- **Syntax Variations**: Markdown incorporates syntax markers (`#`, `**`, `[link](url)`) that can pollute embedding space if left unnormalized.

### The Standardized `LoadedDocument` Representation
The `DocumentLoader` engine extracts and normalizes all input formats into a baseline `LoadedDocument` structure:

```python
@dataclass
class LoadedDocument:
    source_id: str          # Relative path or filename for citation (e.g. "data/sample_corpus/faq_guide.html")
    source_path: str        # Absolute filesystem path
    file_type: str          # Format classifier: "pdf", "html", "md", "txt"
    text_content: str      # Clean, normalized plain text
    char_count: int         # Total extracted character length
    word_count: int         # Total word count
    status: str             # Processing status: "SUCCESS" or "FAILED"
    error_message: str      # Descriptive failure reason (if status == "FAILED")
    loaded_at: str          # ISO-8601 UTC timestamp
```

## 2. Challenges of Extracting Text: PDF vs. Plain Text & HTML

| Metric / Dimension | Plain Text (`.txt`) & Markdown (`.md`) | HTML Exports (`.html`) | PDF Documents (`.pdf`) |
|---|---|---|---|
| **Data Encoding** | Contiguous UTF-8 / ASCII strings. | UTF-8 HTML DOM string. | Complex binary stream containing compressed object streams, font maps, and glyph placement matrices. |
| **Parsing Complexity** | Low (Direct file read with encoding fallback). | Medium (DOM parsing using `BeautifulSoup` to strip `<script>` & `<style>`). | High (`pypdf` page object traversal, glyph-to-char mapping, multi-column ordering). |
| **Layout Extraction** | Natural line breaks and paragraph spacing. | Structured HTML headers and paragraph boundaries. | Non-linear glyph positions; risk of missing text spaces or merging distinct columns. |
| **Corrupt File Risk** | Zero (Fallback to `latin-1` with replacement characters). | Low (Graceful HTML parser recovery). | High (Truncated byte stream, missing EOF marker, encrypted PDF stream). |

### Key Technical Mitigations
1. **PDF Text Extraction**: Uses `pypdf.PdfReader` to iterate page by page, joining extracted page strings with double line breaks.
2. **HTML Sanitization**: Uses `BeautifulSoup` to strip non-content elements (`<script>`, `<style>`, `<head>`, `<meta>`) and extract clean text using `soup.get_text(separator="\n", strip=True)`.
3. **Encoding Resiliency**: Plain text and Markdown parsers attempt `utf-8` decoding first and seamlessly fall back to `latin-1` with replacement characters if binary noise is encountered.

## 3. Preservation of Source Identity (Citation Lineage)

For an enterprise RAG system, every answer generated by the LLM must be traceable back to its origin document.

### Source ID Strategy
The `DocumentLoader` automatically generates a deterministic `source_id` relative to the workspace baseline directory (`base_dir`):
- `data/sample_corpus/company_policy.pdf`
- `data/sample_corpus/employee_handbook.txt`
- `data/sample_corpus/faq_guide.html`

When documents are split into chunks and stored in vector databases (e.g. ChromaDB), `source_id` is embedded directly into chunk metadata. This enables downstream RAG prompt templates to append exact source citations:
```text
Context [Source: data/sample_corpus/faq_guide.html]:
"Immediately notify the InfoSec response team at security@lextrace.internal..."
```

## 4. Graceful Error & Fault Tolerance Handling

A production RAG ingestion job must never crash when encountering a corrupted or invalid file in a directory of thousands of documents.

`DocumentLoader` implements isolated error boundaries for three failure classes:

```
                          [ File Path Input ]
                                  │
                  ┌───────────────┴───────────────┐
                  ▼                               ▼
          [ File Exists? ] ──No──► [ Status: FAILED | "File not found" ]
                  │
                 Yes
                  ▼
        [ Allowed Format? ] ──No──► [ Status: FAILED | "Unsupported format" ]
                  │
                 Yes
                  ▼
         [ Format Parser ] ──Error─► [ Status: FAILED | "PdfStreamError" / Exception ]
                  │
               Success
                  ▼
        [ Status: SUCCESS | Text Extracted & Sample Printed ]
```

1. **Missing Files (`FileNotFoundError`)**:
   - Captured immediately before opening. Returned as `LoadedDocument(status="FAILED", error_message="File not found: ...")`.
2. **Corrupt Binary PDFs (`pypdf.errors.PdfStreamError`)**:
   - Trapped inside format parser boundary. Logs exact error stream issue while allowing remaining files in directory to complete.
3. **Unsupported File Extensions (`.png`, `.exe`, `.zip`)**:
   - Flagged during format validation. Returns explicit unsupported format message without opening binary stream.
